# 커밋 메시지 포맷 스펙

```
<type>(<scope>): <제목>

<본문>

<푸터>
```

## type (필수)

| type | 사용 시점 |
|---|---|
| feat | 사용자에게 보이는 기능 추가 |
| fix | 버그 수정 |
| refactor | 동작 변화 없는 구조 개선 |
| perf | 성능 개선 |
| docs | 문서, 주석, README |
| test | 테스트 추가·수정 |
| build | 빌드 설정, 의존성 |
| ci | CI 파이프라인 설정 |
| chore | 위 어디에도 안 맞는 잡무 |
| revert | 이전 커밋 되돌리기 |

판단 기준: 사용자 눈에 보이는 동작이 바뀌면 feat 또는 fix, 아니면 나머지.
DB 마이그레이션은 스키마 추가면 feat, 결함 보정이면 fix.

## scope (선택)

변경이 한 모듈에 모여 있을 때만 붙인다. 여러 모듈에 걸치면 생략한다.
저장소에서 실제로 쓰는 디렉터리·모듈 이름을 쓴다. 예: `auth`, `crawler`, `mail`, `db`.

## 제목 (필수)

- 한국어 개조식으로 쓴다. 예: "로그인 세션 만료 처리 추가"
- 마침표를 찍지 않는다
- 50자 이내를 권장하고 72자를 넘기지 않는다
- "~했음", "~함" 같은 종결이나 영어 명령형 번역투("Add ~")를 쓰지 않는다
- 무엇이 바뀌었는지가 드러나야 한다. "수정", "버그 픽스" 같은 단독 명사는 금지
- 변경 단위가 여러 개면 `·` 로 나열한다. 예: "ACTIVE 슬롯 강조·마이그레이션 0개 숨김"

## 본문 (선택)

- 제목과 빈 줄 하나로 구분한다
- 왜 바꿨는지, 어떤 대안을 버렸는지를 쓴다. diff를 읽으면 알 수 있는 내용은 반복하지 않는다
- 제목만으로 충분한 변경에는 본문을 붙이지 않는다

본문 규칙은 **구조**(번호 계층)와 **문체**(끊어 쓰기) 두 가지다.

### 구조 — 변경 단위가 2개 이상이면 번호 계층으로 묶는다

`기존:` `변경:` `사유:` 를 평평하게 나열하면 항목이 늘수록 **어느 사유가 어느 변경의 것인지** 알 수 없다.
변경 단위마다 번호를 매기고, 그 단위에 속한 사실은 아래에 들여써서 붙인다.

```
1. <변경 단위 — 무엇을>
   - <대상>: <내용>
   - 사유: <왜>
2. <변경 단위>
   - <대상>: <기존> → <변경>
```

**번호 줄**

- 변경 단위 하나를 명사형 한 줄로 요약한다. 라벨(`변경:` 등)을 붙이지 않는다
- 제목에 `·` 로 여러 항목을 나열했다면 번호 항목과 **순서·표현을 맞춘다**
- 제목이 한 주제면 그 주제의 측면(경로·규칙·화면·문서 등)으로 번호를 나눠도 된다

**하위 줄**

- 3칸 들여쓰기 + `- `. 그 번호 항목에만 속하는 사실만 둔다
- 무엇이 바뀌었는지는 바뀐 **대상 이름**을 라벨로 쓴다: `배지:` `캐시:` `토큰:` `변경 열:`
  - 대상이 번호 줄 자체라 따로 부를 이름이 없으면 `변경:`
- 맥락 라벨: `기존:` `사유:` `원인:` `대체:` `영향:` `주의:` `전제:` `유지:` `확인:`
- 전후 비교는 한 줄로 쓸 수 있다: `- 마이그레이션 표시: 항상 → 있을 때만`
- `기존:` 이 곧 바꾼 이유라면 `사유:` 한 줄로 합친다
- 깊이는 2단계까지. 하위 줄 아래에 또 들여쓰지 않는다

**예외·한도**

- 변경 단위가 **1개**면 번호 없이 들여쓰기 없는 `- ` 목록만 쓴다
- 여러 번호 항목에 공통인 사유·주의는 번호 목록 뒤에 빈 줄 하나를 두고 번호 없는 `- ` 줄로 쓴다
- 번호 항목이 5개를 넘으면 관심사가 섞였는지 먼저 보고 커밋 분할을 제안한다
- `#` 으로 시작하는 줄을 쓰지 않는다 — git 이 주석으로 보고 지운다

```
(나쁨) 사유가 어느 변경의 것인지 불명
기존: ACTIVE 배지가 옅은 틴트라 Standby 와 구분 어려움
변경: ACTIVE 배지를 기본색 채움과 깜빡이는 점으로 표시
변경: Active 카드 틴트 강화와 테두리 색 적용
기존: 변경 열에 마이그레이션 0개가 항상 표시
변경: 마이그레이션은 있을 때만 표시
사유: 마이그레이션이 있는 배포가 눈에 띄도록

(좋음)
1. ACTIVE 슬롯 강조
   - 배지: 기본색 채움 + 깜빡이는 점
   - 카드: 틴트 강화 + 테두리 색
   - 사유: 옅은 틴트로는 Standby 와 구분 어려움
2. 마이그레이션 0개 숨김
   - 변경 열: 있을 때만 표시
   - 사유: 마이그레이션이 있는 배포가 눈에 띄도록
```

### 문체 — 끊어 쓴다

설명문을 줄바꿈만 해서 넣지 않는다. 한 줄은 한 가지 사실이고, **명사 또는 명사형으로 끊는다.**
번호 줄과 하위 줄 모두 같다.

- 종결어미로 맺지 않는다: `~했다` `~한다` `~된다` `~이다` `~않는다` `~때문이다` 금지
- 끊는 말: **없음 · 있음 · 추가 · 제거 · 변경 · 조정 · 개선 · 수정 · 분리 · 통합 · 유지 · 보류 · 폐기 · 대체**
- 문장 접속사(`그래서` `때문에` `~라서` `~므로`)로 잇지 말고 **라벨로 끊는다** (라벨 목록은 위 구조 절)
- 한 줄은 40자 안팎. 72자를 넘으면 다음 줄로 잇지 말고 줄이거나 두 사실로 나눈다
- 쉼표로 두 사실을 잇지 않는다. 두 가지면 두 줄로 나눈다

```
(나쁨) - 비교 팝업은 한 사람을 깊게 보는 곳이라 사람끼리 나란히 비교할 자리가 없었다
(좋음) - 기존: 사람끼리 나란히 비교할 자리 없음
       - 변경: 담당 쏠림·단계별 적체를 한 화면에서 비교

(나쁨) - 헤더를 한쪽 매핑에만 걸면 개발에서 조용히 빠지기 때문에 두 곳이 공유하게 했다
(좋음) - 사유: 개발은 wwwroot/uploads 로 떨어져 기본 매핑이 먼저 서빙
       - 변경: 두 정적 매핑이 헤더 델리게이트 공유
```

## 푸터 (선택)

- 이슈 연결: `Refs: AX-1234` (브랜치명이나 사용자 언급에서 키를 추출한다)
- 호환성 파괴: `BREAKING CHANGE: <무엇이 깨지고 무엇으로 대체되는지>`
- 되돌리기: `Reverts: <커밋 해시>`
