검증 환경: Chrome headless=new · 1440×900 / 1200×1100 / 500×900 · file:// 직접 로드
모든 판정은 파일을 열어 읽은 코드와 실제 렌더 결과로만 내렸다.

**h1**
- reduced-motion: `--force-prefers-reduced-motion` 로 렌더 → 연출 진입 전에 `h1:655-656` 이 차단하고 정적 최종 화면이 그대로 남음. 6개 입구 모두 표시.
- CDN 장애: `MAP cdn.jsdelivr.net 0.0.0.0` 로 GSAP·Pretendard 를 동시에 죽인 상태에서 렌더 → 정적 최종 화면 + 6개 입구 + 스파크라인까지 정상. `typeof gsap === 'undefined'` 가드(`h1:656`)가 실제로 동작함.
- #step 딥링크: `#step=1`(마지막 슬롯 단어 "고객" + 카드 6장 산개), `#step=3`(원장 5행 전개 + 카운터 214 도달), `#step=6`(격자 완성) 모두 그 장의 **완성 상태**로 정지. `tl.seek(cap, false)`(`h1:1069`)로 콜백을 살려 타이핑·카운터까지 끝낸 상태를 만든다.
- 모바일 500: 2×3 격자, 넘침 없음.
- 6입구 정적: `h1:504-569` 실제 `<a href="../sites/*.html">`. 스크립트를 전부 제거한 사본으로 렌더해도 최종 화면 전체가 나옴.
- 키보드 Enter: 입구는 진짜 `<a href>` 이고 홈에서 `tabindex="0"`(`h1:864`) → Tab→Enter 진입 가능. **다만** `h1:1102-1105` 가 Space 를 전역 가로채기 하는데 예외가 `.node` 포커스와 `INPUT` 뿐이라, `#skip`·`#asksend` 버튼에 포커스가 있을 때 Space 가 버튼을 누르지 않고 일시정지로 먹힌다(WCAG 2.1.1 위반). 그래서 "부분".
- 커서 폴백: **실패.** 아래 실사 항목에서 상술.

**h2**
- reduced-motion: 정지 상태로 07 입구 화면에 바로 서고, `h2:704-706` 의 정적 요약 문단까지 추가로 노출. 다섯 안 중 유일하게 텍스트 요약을 준비해 둔 처리다.
- CDN 장애: 외부 JS 가 없으니 영향 없음. jsdelivr·yes24 둘 다 막고 렌더해도 6개 입구 정상.
- #step 딥링크: `#step=3`(원장 전개 + 214 + 비율 띠), `#step=5`(8열 조인 표), `#step=2`(플레이트 6장) 모두 완성 상태. `body.freeze` 로 등장 모션만 끄고 각 요소의 기본값이 종료 상태라는 규약(`h2:145-148`)이 실제로 지켜진다.
- 모바일 500: 500폭에서 조인 표 8열이 가로 스크롤 없이 다 들어감(`h2:446` 이 `min-width` 를 0 으로 되돌림). 플레이트도 2열로 재배치되어 넘침 없음.
- 6입구 정적: **부분.** `h2:692-699` 의 `<nav id="entryIdx">` 는 분명히 정적 마크업이다. 그러나 그 조상인 `.stp` 가 `display:none`(`h2:108`)이고 `.live` 는 JS 만 붙인다. **스크립트를 제거한 사본으로 렌더한 결과, 상·하단 바와 프레임만 남고 무대는 완전히 비었다. 6개 입구가 하나도 보이지 않는다.** 마크업에 있으나 도달 불가 — 이 구분이 이번 판정의 핵심이다.
- 키보드 Enter: 평범한 `<a href>` 이고 keydown 핸들러(`h2:1129-1140`)가 Enter 를 건드리지 않는다. 마지막 장에서는 Space·Arrow 도 조기 반환하므로 입구 순회 중 방해가 없다. 통과.

## 안별 기술 실사

### h1 — 폴백 설계는 최고, 그런데 커서가 실제로 죽어 있다

1. **정적 우선 구조가 말뿐이 아니다.** 문서의 기본 상태가 완성된 최종 화면이고, `.js` 가 붙어야만 시네마틱으로 전환된다. JS 제거·GSAP 차단·reduced-motion 세 경로 모두에서 6개 입구가 살아남는 것을 렌더로 확인했다. 사내 포털이 `script-src 'self'` 같은 CSP 를 걸어 인라인 스크립트를 막는 상황에서도 h1 은 최종 화면이 남는다.

2. **`gsap.killTweensOf('*')` 가 마그네틱 커서를 죽인다 — 재현 검증 완료.** `hardState()` 첫 줄(`h1:826`)이 문서 전체 요소의 트윈을 죽인다. 커서는 `h1:1132-1133` 에서 `gsap.quickTo` 로 만들어지는데, 이 IIFE 는 `boot()`(`h1:1195`)보다 먼저 실행되므로 **부팅 직후 `go(0) → hardState(0)` 에서 이미 killed 된다.** GSAP 3.12.5 로 동일 순서를 재현한 결과: 예외는 나지 않고 조용히 무력화된다 — `quickTo(400)` 후에도 x 는 100 에 머물렀고, 두 번째 kill 후 `quickTo(900)` 도 x=100 그대로였다. 실제 화면에서는 첫 `mousemove` 때 `gsap.set`(`h1:1140`)으로 커서가 한 번 놓이고 동시에 `.cursor-on` 이 붙어 **네이티브 커서가 숨겨진 뒤, 커스텀 커서는 그 자리에 얼어붙는다.** 즉 최근 수정(`h1:370-373`)은 "GSAP 이 아예 안 뜨는" 경우만 막았고 "GSAP 은 떴는데 트윈이 죽은" 이번 경우는 못 막는다. 6개 카드를 클릭해야 하는 화면에서 포인터가 보이지 않는다 — 데스크톱 세션 100% 에서 발생한다.

3. **부팅 베일의 1.6초.** `h1:14-15` 가 `html.boot` 로 body 를 `visibility:hidden` 처리하고 1.6초 안전 타이머로 벗긴다. GSAP 이 죽으면 즉시 벗겨지지만, jsdelivr 가 **죽지 않고 느린**(사내 프록시가 물고 늘어지는) 흔한 경우엔 최대 1.6초 백지 뒤에 화면이 뜬다. 정적 우선이 강점인 문서에 스스로 백지 구간을 만든 셈이다. 상한이 정해져 있다는 점은 인정하되, 순수 정적 HTML 인 h2 대비 명확한 손해다.

4. **상시 루프는 없다.** 자체 rAF 가 없고 모든 연출이 종료되는 GSAP 타임라인이다. 다만 `visibilitychange` 처리가 없어 탭이 가려져도 자동 진행 체인(`h1:1048`)이 브라우저 rAF 스로틀에만 의존한다. 누수는 아니지만 h2 처럼 명시적으로 다루지는 않았다.

5. **유지보수 부담은 `hardState()` 에 몰려 있다.** `h1:825-870` 45줄이 15개 셀렉터에 대해 명령형 `gsap.set` 을 건다. 어느 장에 요소를 하나 추가할 때마다 이 함수에 리셋을 추가하지 않으면 장 사이에 상태가 새어 나온다. 게다가 `killTweensOf('*')` 는 문서 전체를 훑으므로, 이 티저를 요소가 많은 포털 페이지 안에 끼워 넣으면 스텝 전환마다 O(DOM) 비용이 붙고 **모듈 바깥의 트윈까지 죽인다.** 지금 커서가 당한 그대로 다른 것도 당한다.

### h2 — 이식은 가장 싸고 수명주기는 가장 깔끔한데, JS 하나에 전부를 걸었다

1. **의존성 0 이 실측으로 확인된다.** 외부 `<script>` 태그가 없고, jsdelivr·yes24 를 모두 차단해도 렌더가 온전하다. 포털 반입 시 서드파티 승인·버전 고정·자체 호스팅 티켓이 통째로 사라진다. 파일 하나 복사로 끝난다.

2. **rAF 수명주기가 다섯 안 중 가장 정확하다.** `loop()` 는 `cur<LAST && !document.hidden` 일 때만 다음 프레임을 요청하고(`h2:1050-1054`), 마지막 장 진입 시 `stopLoop()`(`h2:1100`), `visibilitychange` 에서 rAF 와 `setTimeout` 을 함께 세우고 복귀 시 `pausedAt` 으로 이어붙인다(`h2:1143-1156`). 카운터도 `rec.stop` 플래그로 일괄 취소된다(`h2:993`). 이 부분은 그대로 가져다 써도 된다.

3. **그런데 CSS 상시 루프가 하나 남아 있다.** `.tex.grain`(`h2:56-61`)은 `position:fixed; inset:0` 전체 화면 레이어에 `mix-blend-mode:overlay` 를 걸고 `grainshift .6s steps(1) infinite` 를 돌린다. `body.freeze`·reduced-motion 이 아닌 한 **종료 화면(07 입구)에서도 영구히 돈다.** blend-mode 는 페이지를 별도 합성 레이어로 밀어내고, 키프레임 3구간이 0.6초마다 배경 위치를 바꿔 뷰포트 전체를 다시 칠한다. 초당 5회 전면 리페인트를 사용자가 가장 오래 머무는 화면에서 계속하는 셈이라, 내장 GPU 사무용 PC 에서 h2 의 유일한 실질 부하다.

4. **콘텐츠의 75% 가 JS 문자열 템플릿이다.** 00 의 6칸(`h2:818`), 02 플레이트(`h2:851-860`), 03 원장(`h2:879`), 04 격자(`h2:915-917`), 05 표(`h2:927-934`), 06 사실카드(`h2:947`) — 8장 중 6장의 마크업이 `innerHTML` 문자열 안에 있다. 빌더를 각각 try/catch 로 격리한 것(`h2:963-965`)은 좋은 판단이지만, 문구 수정이라는 가장 잦은 요청이 전부 JS 편집이 된다.

5. **그리고 그 JS 가 죽으면 화면이 통째로 빈다.** `.stp{display:none}`(`h2:108`) 기본값 + JS 가 붙이는 `.live` 구조 때문에, 스크립트 제거 사본은 검은 사각형과 상·하단 바만 남았다. 빌더는 격리했지만 `go()`·keydown·기동 블록(`h2:1172-1190`)은 격리되지 않아 여기서 한 번 던지면 같은 결과다. `<noscript>` 도 없다. 확률은 낮지만(인라인 스크립트라 네트워크 무관) 실패하면 손실이 100% 다.

6. **공통 취약점 하나.** 두 안 모두 `:hover, :focus-visible` 을 한 셀렉터 목록에 묶어 뒀다(`h1:170`, `h2:385`). `:focus-visible` 미지원 브라우저는 **규칙 전체를 버리므로** hover 스타일까지 같이 사라진다. 구형 브라우저 지원 범위가 좁다면 두 줄로 분리해야 한다.

## 결론 — h2 를 채택한다

1. **운영 비용이 근본적으로 다르다.** h2 는 외부 의존 0 · 파일 1개다. h1 은 GSAP 72 KB 에 대한 반입 승인·버전 고정·자체 호스팅 결정이 붙고, 그 대가로 최대 1.6초의 백지 구간을 스스로 떠안았다.
2. **h1 에는 데스크톱 세션 100% 에서 재현되는 결함이 이미 들어 있다.** `killTweensOf('*')` 가 부팅 시점에 커서 트윈을 죽여 놓고 `.cursor-on` 으로 네이티브 커서까지 감춘다. 조용히 실패하는(예외도 안 나는) 유형이라 운영 중에 원인 찾기가 가장 비싼 종류다.
3. **양쪽의 최대 약점을 고치는 비용이 비대칭이다.** h2 의 무-JS 백지는 `#ent` 를 기본 표시로 돌리고 JS 가 감추게 뒤집으면 되는 수십 줄 작업이고, 수명주기·딥링크·모바일·reduced-motion 은 이미 다 맞춰져 있다. h1 은 커서를 고쳐도 의존성과 부팅 베일이 그대로 남는다.

단, **아래 1번을 고치기 전에는 배포하지 않는다.** h1 의 정적 우선 구조는 h2 가 갖지 못한 미덕이고, 1번은 그것을 h2 에 이식하는 작업이다.

## 채택안(h2)에서 반드시 고쳐야 할 것

### 1. 무-JS·JS 예외 시 백지 — 최우선, 배포 선결 조건
**`h2/index.html:108`** (`.stp{display:none}`) · **`h2/index.html:692-699`** (`<nav id="entryIdx">`) · **`h2/index.html:1172-1190`** (기동 블록)

07 입구를 문서의 **기본 상태**로 뒤집는다. `.stp` 기본값은 유지하되 `#ent{display:block}` 를 기본으로 두고, IIFE 첫 줄(`h2:723` 직후)에서 `document.body.classList.add("js")` 를 붙인 뒤 `body.js .stp:not(.live){display:none}` 로 JS 가 감추게 한다. 스크립트가 아예 안 돌거나 중간에 던져도 6개 입구가 남는다. 함께 기동 블록(`1172-1190`)을 try/catch 로 감싸고, catch 에서 `go(LAST)` 를 시도하도록 한다. 렌더 검증 결과 현재는 이 경로에서 **입구가 0개** 다.

### 2. 그레인 상시 루프를 종료 화면에서 멈춘다
**`h2/index.html:56-61`** (`.tex.grain` 애니메이션) · **`h2/index.html:1083`** (`on-last` 클래스는 이미 붙고 있다)

`body.on-last .tex.grain{animation:none}` 한 줄을 추가하고, `visibilitychange` 핸들러(`h2:1143-1156`)에서도 rAF 와 함께 그레인을 정지시킨다. 전체 화면 `mix-blend-mode:overlay` 레이어를 초당 5회 다시 칠하는 일을, 사용자가 가장 오래 머무는 입구 화면에서 영구히 할 이유가 없다.

### 3. `snapIn` 키프레임과 플레이트의 안착 각도가 서로 모순이다
**`h2/index.html:135-139`** (`@keyframes snapIn`) · **`h2/index.html:849`** (인라인 `transform:rotate(p.r)`) · **`h2/index.html:864-868`** (`animationend` 리스너)

`snapIn` 은 `to{... rotate(0deg)}` 로 끝나는데 플레이트의 안착 상태는 `rotate(p.r)` 다. 애니메이션이 도는 0.7초 동안 인라인 transform 이 눌려 회전이 0 으로 풀렸다가, `animationend` 리스너가 회전을 **되돌려 붙이면서 끝에서 튄다.** 주석("스냅 애니메이션 종료 후 회전 유지")이 이미 이 모순을 자백하고 있다. 같은 `snapIn` 을 04 정렬 열(`h2:289`)도 쓰는데 그쪽은 rotate(0) 안착이 맞아서, 키프레임 하나가 서로 다른 두 안착 상태를 겸하고 있는 게 원인이다. `to{transform:translate(0,0) rotate(var(--dr,0deg))}` 로 끝내고 04 쪽은 `--dr:0deg` 를 주면 리스너 5줄을 통째로 지울 수 있다.
